## Текущая договорённость с пользователем
- Разработка может идти через WSL Ubuntu и VS Code, но рабочая среда проекта — Windows.
- Проект должен быть удобен для Git: клонировать на Windows-компьютер, настроить `.env`, запустить `.bat`-скрипты и получить Excel.
- Для Codex CLI контекст проекта хранится в `.codex/`.
- Перед новой задачей агент обязан перечитать проектную память.
- Сначала делаем надёжную основу, потом удобства и рефакторинг.
- Пользователь не любит мусор в проектах: периодически чистить артефакты, случайные файлы и устаревшие заметки.
- Предпочтение — модульная структура, понятные типизированные имена файлов и единый стиль похожих модулей.

## Ближайшие шаги
- Держать Windows-first документацию и команды запуска актуальными.
- Модульная структура пакета `lemana_parser/` подготовлена; дальше расширять её без возврата к куче файлов в корне.
- Windows `.bat`-скрипты запускают Python напрямую из `.venv\Scripts\python.exe`.
- Локальная основа покрыта тестами парсинга, конфигурации, Excel-выгрузки, CLI, HTTP/retry и диагностики cookie.
- Служебные команды вынесены в `scripts/`: тесты, полная локальная проверка и очистка dev-артефактов.
- Dev-инструменты вынесены в `requirements-dev.txt`; lint/format/check выполняются через Ruff и `scripts/`.
- Упаковку в `.exe` отложить до полной готовности проекта.
- После полного боевого Windows-прогона от 2026-05-25 выявлено: `batch=3` почти гарантированно вызывает `403`, а `batch=2` с паузой ниже ~2 сек тоже нестабилен. Стратегия карточек ужесточена: активный batch по умолчанию не выше 2, минимальная recovery-пауза 2 сек, cooldown 20 сек, восстановление только после 6 стабильных батчей.
- Отложенные `403/429` карточки теперь проходят до 3 медленных одиночных раундов с паузой 6 сек между товарами, а не один быстрый повтор. Проверить на Windows полный прогон `.\run_win.bat --no-playwright`; ожидаем меньше финальных `http_403`, но время может вырасти.
- После успешного боевого прогона 381/381 без ошибок за ~19.5 минут зафиксировать стабильную стратегию как основной режим. Следующий фокус — самовосстановление cookie: перед парсингом проверять каталог и первую карточку, при `401/403/429` автоматически обновлять cookie через Chrome CDP, затем через Playwright fallback.
- Windows-подсказки должны учитывать PowerShell: корневые `.bat`-скрипты из текущей папки запускать как `.\run_win.bat`, `.\get_cookie.bat`. Сообщения CLI и README обновлены, чтобы не вести пользователя к команде без `.\`.
- Автополучение cookie через `get_cookie.bat` усилено: Chrome открывает каталог через CDP, ждёт до 120 секунд и даёт пользователю время пройти Qrator-проверку.
- `get_cookie.bat` больше не подменяет User-Agent на старый Chrome и использует локальный профиль `.chrome_cdp_profile/`, чтобы сохранять браузерное состояние между автообновлениями cookie.
- Если карточки `/product/...` дают `403`, сначала обновить код, заново получить cookie через `get_cookie.bat` и проверить `main.py --check-cookie --no-pause`: диагностика теперь отдельно показывает статус каталога и первой карточки товара.
- После боевого Windows-прогона от 2026-05-25 в 21:17 подтверждено: автообновление cookie через CDP прошло, полный каталог 381/381 выгружен без ошибок за ~19.7 минуты. Добавлена аккуратная печать логов через `tqdm.write`, чтобы timestamp логов не прилипал к progress bar, и итоговая телеметрия отложенных карточек.
- После боевых прогонов на каталогах 381 и 264 товаров подтверждено: `LEMANA_PRODUCT_MIN_RECOVERY_SLEEP=3.0` не убирает `403`, но может уменьшать давление. Cooldown отвязан от `min_recovery_sleep * 10` и теперь управляется напрямую через `LEMANA_PRODUCT_PRESSURE_COOLDOWN` / `--product-pressure-cooldown` (обычно 15-20 сек).
- Progress bar карточек должен показывать текущее время, текущий `batch`, текущий `sleep`, количество отложенных карточек и антибот-сигналы последнего батча.
- После боевых прогонов с `LEMANA_PRODUCT_BATCH_SLEEP=4.0`, `LEMANA_PRODUCT_MIN_RECOVERY_SLEEP=4.0`, `LEMANA_PRODUCT_PRESSURE_COOLDOWN=15.0` итог стабилен: каталоги 264 и 381 товара завершились без финальных ошибок, а время осталось примерно на уровне предыдущих быстрых настроек. Эти значения нужно считать базовым stable-режимом.
- Добавить и поддерживать CLI-профили загрузки карточек: `stable` для обычной боевой работы, `careful` для максимально бережного запуска, `fast` только для коротких тестов.
- По HAR-файлам подтверждён перспективный API-путь: каталог можно собирать через `hybrid/v1/products:search`, `products-data:search`, `products-media:search` и `getRatings`, чтобы уйти от массовой загрузки HTML-карточек.
- Следующий крупный этап — отдельный API-слой и UI: выбор одной или нескольких категорий, настройка фильтров, запуск выгрузки в Excel, режим по списку артикулов ЛМ, автопроверка/обновление cookie и fallback на текущий стабильный HTML-режим.
- Первый API-слой добавлен: `LEMANA_DATA_SOURCE=api|api-fallback`, CLI `--data-source`, выгрузка по `--articles` / `--articles-file`, API preflight без обязательной проверки HTML-карточки. Нужен боевой Windows-тест `.\run_win.bat --data-source api-fallback --max-products 30`.
- Боевые Windows-тесты API подтверждены: каталог 381 товаров за 6.8 сек, каталог 263 товара за 6.1 сек, выгрузка по артикулам ЛМ работает. `api-fallback` нужно держать основным режимом, HTML оставить резервом.
- Перед финальной продуктовой итерацией проведена стабилизация текущей версии: SSL verification включён по умолчанию через `LEMANA_SSL_VERIFY=true`, API host из PLP-состояния ограничен доменом `lemanapro.ru`, `products-media` больше не валит API-выгрузку целиком, а товары без `products-data` попадают в Excel со статусом `api_data_missing` вместо молчаливой потери строки.
- Локальные capture-файлы `категория.har`, `товар.har`, `лемана.json`, `parser.log` и Python cache удалены из рабочей папки после анализа; в Git остаются только `.env` и `.venv` как игнорируемые локальные файлы.
