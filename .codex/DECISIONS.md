## Решения по работе агента
- Основной источник долгосрочного контекста — файлы в `.codex/`.
- Корневой `AGENTS.md` служит точкой входа для Codex CLI.
- При каждом новом сеансе агент обязан сначала читать инструкции, а не начинать изменения с нуля.
- Рабочая платформа проекта — Windows; WSL используется как среда разработки.
- Упаковку в `.exe` делаем только после полной готовности проекта, не сейчас.
- Мусорные файлы и локальные артефакты не должны попадать в Git.
- Основной код перенесён в пакет `lemana_parser/`; в корне оставлены только wrappers для простого Windows-запуска.
- Для служебных команд использовать `scripts/`, не раздувать корень проекта новыми `.bat`/dev-файлами.
- Cookie из `.env` используется как начальное состояние `curl_cffi` session cookie jar. Не подставлять старую строку `Cookie` вручную в каждый обычный запрос, чтобы серверные `Set-Cookie` могли обновлять состояние сессии.
- Для карточек товаров `403/429` считать антибот-сигналом, а не обычной временной сетевой ошибкой: не делать агрессивные немедленные retry, откладывать товар и повторять позже в одиночном режиме после cooldown.
- Для боевой стабильности карточек приоритет выше скорости: не разгонять активный batch выше 2 без явного решения, не опускать recovery sleep ниже 2 сек и повторять проблемные карточки несколькими медленными раундами.
- Cooldown после антибот-сигналов карточек должен быть прямой настройкой `LEMANA_PRODUCT_PRESSURE_COOLDOWN`, без скрытой формулы от `LEMANA_PRODUCT_MIN_RECOVERY_SLEEP`. Это позволяет держать паузу карточек 3-4 сек, но cooldown оставить 15-20 сек.
- Cookie перед парсингом проверять автоматически: каталог + первая карточка. При проблеме с cookie запускать автообновление через Chrome CDP с постоянным локальным профилем `.chrome_cdp_profile/`, затем Playwright fallback; ручную вставку не считать основным сценарием.
- Базовый боевой режим карточек: `product_batch_sleep=4.0`, `product_min_recovery_sleep=4.0`, `product_pressure_cooldown=15.0`, `product_max_active_batch=2`. Эти значения дают меньше `403` без заметного ухудшения общего времени на последних Windows-прогонах.
- HAR/capture-файлы и сохранённые HTML/JSON-снимки страниц считать локальными чувствительными артефактами: не коммитить, держать в `.gitignore`, после анализа удалять или переносить в локальную ignored-папку.
- UI делать отдельным слоем поверх ядра парсера, а не встраивать в `cli.py`. Текущий CLI оставить стабильным рабочим входом; будущий Windows UI должен переиспользовать общий сервис запуска, API-клиент, Excel writer и cookie recovery.
- Основной путь развития данных — API-first: использовать API сайта для каталога и пачечных данных товаров, а HTML-парсинг оставить как fallback до подтверждения API на боевых Windows-прогонах.
- Для API-режима cookie preflight проверяет каталог, но не обязан проверять HTML-карточку товара: API-режим как раз должен избегать массовых product-page запросов. HTML-режим по умолчанию продолжает проверять первую карточку.
- Для продукта на продажу базовым направлением считать Windows desktop-приложение с локальным ядром, локальным хранением cookie и будущей упаковкой в `.exe`; web/SaaS рассматривать позже, потому что антибот и cookie сильнее привязаны к браузеру и IP пользователя.
- После боевых Windows-прогонов `api-fallback` считать основным режимом запуска. Чистый `html` оставлять как ручной аварийный режим для диагностики и случаев, когда API сайта изменится.
- HTTPS-проверку сертификатов держать включённой по умолчанию (`LEMANA_SSL_VERIFY=true`). Отключение допустимо только как временная диагностика проблемного Windows-компьютера.
- Для Windows с кириллицей в пути проекта не отключать SSL сразу: сначала копировать `certifi` CA bundle в ASCII-путь и использовать этот файл как `verify` для `curl_cffi`.
- API endpoint из HTML-состояния PLP доверять только если он ведёт на HTTPS-домен `lemanapro.ru`; это защищает от случайной отправки запросов на посторонний host при изменённом/битом HTML.
- API-выгрузка не должна молча терять товары: если `products:search` вернул артикул, а `products-data:search` не вернул данные, строка должна попасть в Excel со статусом `api_data_missing`.
- Для произвольного списка `--articles` нельзя считать фасеты текущей категории обязательными: сначала использовать обычный `products-data`, затем для недостающих артикулов делать relaxed retries без категорийных фасетов и eligibility-фильтра, чтобы не отбрасывать товары из других категорий/региональной выдачи.
